# 데이터 설계 표준

## 1. 원칙

- 필요한 최소 데이터만 수집한다.
- 직접 식별정보를 기본 수집하지 않는다.
- 원 IP를 저장하거나 화면에 표시하지 않는다.
- 현재 구현과 목표 데이터모델을 구분한다.
- DB 변경은 코드 배포와 분리하고 복구계획을 마련한다.

## 2. 주요 데이터 영역

### 익명 테스트 세션

- 세션 ID
- Beauty Code
- 생성 방식: 테스트 또는 직접 선택
- 선택형 연령대
- 국가코드
- 광역 지역코드
- 완료 여부
- 생성일시

### 상품 신청

- 신청 ID
- 익명 세션 ID
- 입력 유형: 상품명 또는 URL
- 입력값
- 상품 ID
- 처리상태
- 오류 메시지
- 신청일시

### 상품

- 상품 ID
- 정식 상품명
- 브랜드
- 카테고리
- 공개 상품 URL
- 확인상태
- 생성·수정일시

### 상품별 16유형 적합도

- 상품 ID
- Beauty Code
- 적합도 점수
- 분석 버전
- 분석 요약
- 근거
- 공개 여부
- 생성·수정일시

## 3. 제약조건

- 상품 하나와 Beauty Code 하나의 조합은 유일해야 한다.
- Beauty Code는 `[OD][GM][PC][VE]` 형식이어야 한다.
- 점수는 0~100 범위다.
- 공개 전 16개 유형 점수 존재 여부를 검증한다.
- 상품 신청은 유효한 세션과 연결한다.

## 4. 지역 데이터

- 국가: ISO 국가코드 사용
- 대한민국 지역: 광역 지역코드 사용
- 화면에서 코드명을 서울·부산·경기 등으로 변환
- 지역 확인 불가를 별도 집계

## 5. 테스트 데이터

- 테스트 데이터는 공통 표식 또는 배치 ID를 가진다.
- 상품명에는 필요 시 `[DEMO]`를 사용한다.
- 실제 데이터와 섞이지 않도록 조회·삭제 조건을 갖춘다.
- 삭제 전 대상 건수를 확인한다.

## 6. 보안

- 서비스 역할 키는 서버 환경에서만 사용한다.
- 브라우저에 비밀키를 전달하지 않는다.
- RLS와 권한을 명시적으로 설정한다.
- 관리자 기능은 인증 후 접근하도록 발전시킨다.
- 환경변수 값은 GitHub 문서와 로그에 기록하지 않는다.

## 7. 변경 절차

1. 목표 스키마 작성
2. 현재 데이터와 영향분석
3. 백업 또는 복구방법 확인
4. 마이그레이션 SQL 검토
5. 테스트 환경 실행
6. 코드 호환성 검증
7. 운영 DB 적용 승인
8. 적용 후 행 수·제약·API 확인
9. 변경이력 갱신
