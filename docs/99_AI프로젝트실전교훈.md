# AI 프로젝트 실전 교훈

## 1. 문서 목적

실제 프로젝트에서 발생한 시행착오를 재사용 가능한 컨설팅 자산으로 축적한다. 개인이나 도구를 비난하는 문서가 아니라 다음 프로젝트의 실패를 줄이는 운영지식이다.

## 2. 설계와 개발

- 대화에서 합의한 내용은 자동으로 통합 설계가 되지 않는다.
- 설계를 먼저 문서로 고정하지 않으면 같은 내용을 반복 확인하게 된다.
- 화면 하나의 문구 변경도 서비스 철학, 관리자 KPI, DB와 연결될 수 있다.
- 개발 전에 현재 구현과 목표 설계를 구분해야 한다.

## 3. ChatGPT와 장기 프로젝트

- ChatGPT의 대화 기억만으로 수백 개의 결정을 일관되게 유지하기 어렵다.
- 메모리는 상세 기술문서와 변경이력을 대체하지 않는다.
- 기준 문서를 읽도록 요청하고, 중요한 결정은 GitHub에 저장해야 한다.
- 성공했다고 답한 내용도 실제 저장소·배포·DB로 검증해야 한다.

## 4. Codex와 개발

- 오류를 반복 수정하면 사용량과 시간이 크게 소모된다.
- 작은 검증 단위로 작업하고 실패 시 원인분석을 먼저 해야 한다.
- AGENTS.md만으로 모든 설계를 담지 말고 기준 문서와 역할별 지침을 분리한다.
- 불명확하면 구현을 멈추고 추가 자료를 요청하도록 규칙화한다.

## 5. GitHub

- GitHub는 코드 저장소이자 제품 지식저장소다.
- 브랜치 이름과 폴더 경로를 혼동하지 않도록 정확히 안내해야 한다.
- 운영 브랜치와 문서 브랜치를 분리하면 MVP 안정성을 보호할 수 있다.
- 문서가 실제로 존재하는지 링크와 파일 조회로 확인해야 한다.

## 6. 배포와 데이터베이스

- 커밋 완료와 배포 완료는 다르다.
- 배포 `pending` 상태를 완료라고 표현하면 안 된다.
- 코드에 필요한 테이블이 실제 DB에 없을 수 있다.
- 권한 오류, 스키마 오류, 환경변수 오류를 구분해야 한다.
- DB 변경은 SQL 실행 여부와 실제 조회 결과까지 확인해야 한다.

## 7. 비용과 AI 자동화

- ChatGPT Plus와 OpenAI API는 별도 서비스와 과금체계다.
- MVP에 자동분석이 반드시 필요한 것은 아니다.
- 수동 운영으로 가치와 기준을 검증한 뒤 자동화할 수 있다.
- 오너에게 비용·제약·운영부담을 사전에 설명해야 한다.

## 8. 사용자 가치

- 기능 목록보다 사용자가 얻는 핵심 답을 먼저 정의해야 한다.
- LAYAD의 핵심은 16유형 자체가 아니라 사용자 유형과 상품의 적합도다.
- 기술적인 표현보다 사용자가 이해하고 신뢰할 수 있는 문구가 중요하다.
- 히트맵과 통계는 핵심 답을 돕는 수단이지 목적이 아니다.

## 9. 컨설팅 자산화

- 프로젝트 경험을 사업자료와 기술자료로 분리해 기록한다.
- 실패와 수정 이유를 의사결정 기록에 남긴다.
- 작은 MVP 경험도 대형 AI 전략·시스템 프로젝트의 운영 원칙으로 확장할 수 있다.
- 고객에게는 도구가 아니라 재사용 가능한 운영체계를 남겨야 한다.

## 10. 다음 프로젝트 시작 전 질문

- 기준 문서는 어디에 있는가?
- 현재 상태와 목표 상태가 분리되어 있는가?
- 운영 시스템을 보호하는 트랙이 있는가?
- 누가 개발과 배포를 승인하는가?
- AI 비용과 개인정보 정책이 설명됐는가?
- 테스트와 복구 기준이 있는가?
- 완료를 증명할 객관적 근거가 있는가?
