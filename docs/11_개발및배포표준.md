# 개발 및 배포 표준

## 1. 목적

운영 중인 MVP의 안정성을 보호하면서 승인된 요구사항을 작은 단위로 개발·검증·배포한다.

## 2. 브랜치 원칙

- `main`: 운영 기준 브랜치
- 문서 브랜치: 설계·표준·컨설팅 자료
- 기능 브랜치: 승인된 개발 작업
- 긴급수정 브랜치: 운영 장애 복구

문서 브랜치에서 운영 코드와 DB를 수정하지 않는다.

## 3. 개발 전 확인

- 요구사항이 `DESIGNED` 상태인가
- 사용자에게 개발 승인을 받았는가
- 현재 코드와 DB를 읽었는가
- 영향받는 화면·API·테이블을 식별했는가
- 실패 시 복구방법이 있는가
- 테스트 기준이 작성됐는가

## 4. 개발 단위

- 한 번에 하나의 핵심 문제를 해결한다.
- 관련 없는 리팩터링을 함께 수행하지 않는다.
- 기존 동작을 유지하는 것을 기본값으로 한다.
- DB, API, UI 변경은 가능하면 단계적으로 분리한다.
- 오류 반복 시 추가 수정을 멈추고 원인을 재분석한다.

## 5. 배포 단계

1. 코드 검토
2. 정적 검사와 빌드
3. 미리보기 환경 검증
4. DB 마이그레이션 승인과 실행
5. 운영 배포 승인
6. 운영 배포
7. 사용자·관리자 핵심경로 확인
8. 데이터 저장·조회 확인
9. 오류 로그 확인
10. 요구사항 상태와 배포기록 갱신

## 6. DB 변경

- 코드 배포와 DB 변경을 구분한다.
- 기존 컬럼 삭제·형식변경은 특히 신중히 검토한다.
- 가능하면 추가형 마이그레이션을 우선한다.
- 적용 전 대상 테이블과 데이터 건수를 확인한다.
- SQL은 재실행 가능성과 부분 실패를 고려한다.
- 운영 적용 후 스키마 캐시와 API 응답을 확인한다.

## 7. 환경변수

- 필요한 변수명과 용도를 문서화하되 값은 기록하지 않는다.
- Preview와 Production 범위를 구분한다.
- 변수 변경 후 재배포 필요 여부를 확인한다.
- OpenAI API 등 별도 과금서비스는 사전 승인 없이 추가하지 않는다.

## 8. 복구 원칙

- 직전 안정 커밋을 기록한다.
- 코드 롤백과 DB 복구를 별도로 준비한다.
- 장애 발생 시 신규 기능을 중단하고 사용자 핵심경로를 우선 복구한다.
- 복구 후 원인과 예방조치를 장애 기록에 남긴다.

## 9. 완료 정의

다음 조건을 모두 충족해야 완료다.

- 승인된 범위 구현
- 빌드 성공
- 운영 배포 성공
- 실제 운영주소 확인
- DB 저장·조회 확인
- 모바일·PC 핵심경로 확인
- 문서와 상태 갱신

커밋만 존재하거나 배포가 `pending`인 상태는 완료가 아니다.
