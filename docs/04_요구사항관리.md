# 요구사항 관리

## 1. 목적

대화, 회의, 설계, 개발, 배포 상태를 구분하여 같은 내용을 반복 확인하거나 미개발 기능을 완료로 오해하는 일을 방지한다.

또한 결정된 사항만 문서에 반영하고, 개발·배포·검증 결과에 따라 관련 문서를 지속적으로 현행화한다.

## 2. 상태

| 상태 | 의미 |
|---|---|
| IDEA | 논의 중 |
| DESIGNED | 설계 확정, 미개발 |
| DEVELOPED | 코드 반영 완료 |
| DEPLOYED | 운영환경 반영 완료 |
| VERIFIED | 실제 화면·데이터 검증 완료 |
| DEFERRED | 보류 |
| REJECTED | 폐기 |

## 3. 필수 항목

- 요구사항 ID
- 요청일
- 요청 내용
- 목적과 사용자 가치
- 현재 상태
- 영향 화면
- 영향 API·DB
- 테스트 기준
- 승인 여부
- 관련 문서
- 관련 커밋 또는 배포정보
- 최종 현행화 일자

## 5. 변경 규칙

- 요구사항을 바로 개발하지 않고 영향분석 후 `DESIGNED`로 확정한다.
- 논의 중인 아이디어는 확정 요구사항으로 문서화하지 않는다.
- 개발 승인과 배포 승인을 구분한다.
- 배포 후 실제 확인 전에는 `VERIFIED`로 변경하지 않는다.
- 범위가 커지면 하나의 요구사항을 여러 검증 가능한 작업으로 분리한다.
- 충돌하는 요구사항은 구현 전에 프로젝트 헌장과 의사결정 기록을 갱신한다.

## 6. 상태별 문서 현행화

### DESIGNED

- 목표설계
- 사용자·관리자 UX 표준
- 데이터 설계 표준
- 의사결정 기록
- 개발 백로그

### DEVELOPED

- 요구사항 상태
- 기술구현 내용
- API·DB 변경사항
- 테스트 항목
- 관련 커밋

### DEPLOYED

- 배포 환경
- 배포 일시
- 배포 버전 또는 커밋
- 알려진 제약사항

### VERIFIED

- 현재 MVP 현황
- 실제 화면·데이터 검증 결과
- 완료된 요구사항
- 잔여 오류와 후속과제

## 8. 완료 기준

다음 조건이 모두 충족돼야 요구사항 변경이 종료된 것으로 본다.

1. 결정사항이 관련 문서에 반영됨
2. 개발 또는 설계 상태가 정확히 기록됨
3. 테스트 결과가 기록됨
4. 배포 여부가 기록됨
5. 실제 검증 여부가 기록됨
6. 관련 문서가 현재 상태와 일치하도록 현행화됨
