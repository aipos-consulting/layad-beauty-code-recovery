# 요구사항 관리

## 1. 목적

대화, 회의, 설계, 개발, 배포 상태를 구분하여 같은 내용을 반복 확인하거나 미개발 기능을 완료로 오해하는 일을 방지한다.

## 2. 상태

| 상태 | 의미 |
|---|---|
| IDEA | 논의 중 |
| DESIGNED | 설계 확정, 미개발 |
| DEVELOPED | 코드 반영 완료 |
| DEPLOYED | 운영환경 반영 완료 |
| VERIFIED | 실제 화면·데이터 검증 완료 |
| DEFERRED | 보류 |
| REJECTED | 폐기 |

## 3. 필수 항목

- 요구사항 ID
- 요청일
- 요청 내용
- 목적과 사용자 가치
- 현재 상태
- 영향 화면
- 영향 API·DB
- 테스트 기준
- 승인 여부
- 관련 커밋 또는 배포정보

## 4. 등록 예시

| ID | 요구사항 | 상태 | 검증 기준 |
|---|---|---|---|
| REQ-001 | 사용자 유형 기준 상품 적합도 표시 | DESIGNED | 점수·등급·순위 표시 |
| REQ-002 | 16유형 히트맵 | DESIGNED | 사용자 유형과 최고점 강조 |
| REQ-003 | 모바일 관리자 전체 메뉴 | DEPLOYED | 7개 메뉴 접근 가능 |

## 5. 변경 규칙

- 요구사항을 바로 개발하지 않고 영향분석 후 `DESIGNED`로 확정한다.
- 개발 승인과 배포 승인을 구분한다.
- 배포 후 실제 확인 전에는 `VERIFIED`로 변경하지 않는다.
- 범위가 커지면 하나의 요구사항을 여러 검증 가능한 작업으로 분리한다.
- 충돌하는 요구사항은 구현 전에 프로젝트 헌장과 의사결정 기록을 갱신한다.
