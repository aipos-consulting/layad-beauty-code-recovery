# AI 기반 제품개발 컨설팅 가이드

## 1. 컨설팅 핵심 메시지

AI 개발의 실패 원인은 코딩 능력 부족만이 아니다. 더 자주 발생하는 원인은 다음과 같다.
- 비즈니스 설명과 기술 설계가 섞임
- 대화 속 결정이 문서로 남지 않음
- 설계와 구현 상태를 구분하지 않음
- 빠른 배포가 운영 안정성을 침해함
- AI가 기존 의사결정을 자동으로 완전 통합할 것이라고 기대함

## 2. 권장 산출물 체계

### Business Track
오너와 의사결정자를 위한 자료
- 문제 정의
- 고객 가치
- 수익모델
- 투자·예산
- 로드맵
- KPI

### Product Track
제품 책임자와 컨설턴트를 위한 기준
- 제품 비전
- 사용자 경험 원칙
- 업무 규칙
- 데이터 정책
- AI 정책
- 의사결정 이력

### Technical Track
개발자와 AI 코딩 도구를 위한 자료
- 아키텍처
- DB 스키마
- API 명세
- 화면 상태와 오류 처리
- 보안·환경변수
- 테스트·배포·복구 절차

## 3. 2트랙 실행 모델

### 운영 트랙
- 현재 서비스 안정성 우선
- 장애와 핵심 결함만 작은 단위로 수정
- 변경 전후 회귀 테스트

### 혁신 트랙
- 문서, 설계, 실험, 차기 기능
- 별도 브랜치 또는 별도 환경
- 승인 전 Production 반영 금지

## 4. AI 도구 운영 원칙

- ChatGPT: 요구사항 정리, 대안 비교, 문서 초안, 검토
- Codex: 저장소 문서를 읽고 제한된 개발 과업 수행
- GitHub: 제품 지식과 변경 이력의 기준 저장소
- CI/CD: 테스트와 배포의 자동 안전장치

AI에게 매번 전체 맥락을 기대하지 말고, 저장소 문서를 읽도록 강제한다.

## 5. 비개발자 오너·컨설턴트 체크리스트

개발 지시 전:
- 목적이 한 문장으로 정의됐는가
- 현재 상태와 목표 상태가 구분됐는가
- 개인정보·비용·운영 책임을 확인했는가
- 성공 기준과 실패 시 복구 방법이 있는가

배포 지시 전:
- 변경 범위가 작은가
- 테스트 결과를 확인했는가
- DB 변경과 코드 변경을 분리했는가
- Preview에서 확인했는가
- 기존 사용자의 경로가 유지되는가

배포 후:
- 운영 주소에서 직접 확인했는가
- 로그와 DB 저장을 확인했는가
- 상태를 VERIFIED로 갱신했는가
- 결정과 문제를 문서에 남겼는가

## 6. 기업 적용 시 권고

중소기업은 직원 개인에게 AI 비용과 책임을 전가하지 않아야 한다. 오너가 비용을 부담하려면 다음을 제시해야 한다.
- 업무별 시간 절감
- 오류 감소
- 처리량 증가
- 고객 반응 개선
- 운영 비용과 AI 비용 비교

개인 생산성 도구와 조직 프로세스용 AI 에이전트를 구분하여 도입한다.

## 7. LAYAD 사례의 교훈

- MVP를 만들면서 제품 철학이 발전할 수 있다.
- 발전된 철학은 화면 하나가 아니라 UI, DB, KPI, 운영정책 전체에 반영돼야 한다.
- 대화는 탐색에 유용하지만 최종 기준은 GitHub 문서여야 한다.
- 뒤늦은 문서화도 가능하지만 운영 코드와 분리하여 진행해야 한다.
