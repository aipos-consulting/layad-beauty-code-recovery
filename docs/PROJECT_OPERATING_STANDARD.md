# LAYAD AI 기반 제품개발 표준

## 1. 목적

이 문서는 LAYAD MVP를 안정적으로 운영하면서, 설계·기술자료·컨설팅 자산을 별도 트랙으로 축적하기 위한 표준이다.

핵심 원칙은 다음과 같다.

> 운영 중인 MVP는 안정성을 우선하고, 설계와 기술 표준화는 별도 트랙에서 진행한다.

## 2. 2트랙 운영 모델

### Track A — MVP 안정화·운영

목표: 현재 배포된 서비스의 안정성 유지와 사용자 데이터 축적

포함 범위:
- 현재 운영 화면과 API
- Supabase 연결
- 사용자 유형조회와 상품 신청
- 관리자 조회 기능
- 긴급 오류 수정
- 운영 데이터 보호

운영 원칙:
- 승인 없는 기능 변경 금지
- DB 구조 변경 전 백업·영향분석 필수
- 한 번에 하나의 작은 변경만 반영
- 배포 후 핵심 경로 회귀 테스트
- 실패 시 직전 안정 버전으로 복구

### Track B — 설계·기술표준·차기 기능

목표: 대화에 흩어진 지식을 문서화하고 차기 개발의 기준을 수립

포함 범위:
- 제품 철학과 UX 원칙
- 사용자-상품 적합도 중심 설계
- 관리자 화면 설계
- DB·API 목표 구조
- AI 운영 정책
- 문구와 톤앤매너
- 미개발 기능 백로그
- 컨설팅 방법론

운영 원칙:
- 문서 전용 브랜치에서 작업
- 운영 코드와 DB는 변경하지 않음
- 설계 확정과 개발 완료를 구분
- 검토 후 필요한 항목만 Track A로 이관

## 3. 문서 계층

1. `MASTER_DESIGN.md` — 제품 철학과 절대 원칙
2. `MVP_CURRENT_STATE.md` — 현재 실제 동작 상태
3. `TARGET_DESIGN.md` — 목표 설계
4. `DECISION_LOG.md` — 의사결정 이유와 영향
5. `BACKLOG.md` — 설계됐지만 미개발인 항목
6. `AGENTS.md` — ChatGPT·Codex 작업 규칙
7. `CONSULTING_GUIDE.md` — 타 기업 컨설팅에 재사용할 방법론

문서 우선순위:

`MASTER_DESIGN > 승인된 DECISION_LOG > TARGET_DESIGN > BACKLOG > 대화 중 아이디어`

충돌 시 구현하지 않고 먼저 문서를 정리한다.

## 4. 요구사항 상태 모델

모든 요구사항은 다음 상태 중 하나를 가진다.

- `IDEA`: 논의 중
- `DESIGNED`: 설계 확정, 미개발
- `DEVELOPED`: 코드 반영 완료, 배포 미확인
- `DEPLOYED`: 운영 주소에서 확인 완료
- `VERIFIED`: 실제 데이터와 핵심 경로 검증 완료
- `DEFERRED`: 보류
- `REJECTED`: 폐기

상태가 없는 요구사항은 개발 대상으로 간주하지 않는다.

## 5. 변경 절차

1. 요구사항 접수
2. 기존 문서·코드·DB 영향 확인
3. 목표 설계 문서 수정
4. 상태를 `DESIGNED`로 기록
5. 사용자의 명시적 개발 승인
6. 작은 단위로 개발
7. 테스트
8. 배포 승인
9. 배포
10. 실제 화면·데이터 검증
11. 상태와 변경이력 갱신

## 6. 배포 안전 원칙

- 문서 브랜치는 운영 배포 대상이 아니다.
- 기능 브랜치에서 개발하고 Preview에서 확인한다.
- Production 배포는 사용자의 명시적 지시가 있을 때만 한다.
- DB 마이그레이션은 코드 배포와 분리한다.
- 테스트 데이터는 식별자를 넣고 일괄 삭제 가능해야 한다.
- 환경변수와 비밀키는 문서·코드·화면에 노출하지 않는다.
- 배포 전 핵심 사용자 경로와 관리자 경로를 각각 검증한다.

## 7. 회귀 테스트 최소 항목

사용자 경로:
- 첫 화면 진입
- 20문항 테스트 완료
- Beauty Code 직접 선택
- 연령대 선택
- 상품명·링크 신청
- 신청 상태 표시
- 저장 성공 여부

관리자 경로:
- `/admin` 진입
- 사용자 통계 조회
- 상품 신청 조회
- 모바일 메뉴 전체 접근
- Supabase 오류 처리

데이터:
- 테스트·직접선택 구분
- 연령대 집계
- 국가·지역 집계
- 상품 신청과 세션 연결
- 테스트 데이터 식별·삭제

## 8. 핵심 제품 방향

LAYAD의 중심은 상품 인기나 유형 분포가 아니다.

> 선택하신 상품이 회원님의 Beauty Code와 얼마나 잘 맞는지 알려주는 서비스

따라서 사용자와 관리자 화면 모두 다음 정보를 우선한다.
- 사용자 Beauty Code
- 신청 상품
- 해당 유형 적합도 점수
- 적합도 등급
- 16유형 내 순위
- 적합도 근거
- 16유형 히트맵

## 9. 정기 점검

매 개발 주기 종료 시 다음을 점검한다.
- 현재 구현과 문서가 일치하는가
- 설계만 된 기능이 구현된 것으로 오해되지 않는가
- 운영 안정성을 해치는 변경이 없는가
- 신규 결정이 다른 화면·DB·KPI에 미치는 영향이 반영됐는가
- 변경 이유가 DECISION_LOG에 남아 있는가
